# Do agents report success they can see is false?

A behavioral study of **false success claims** in tool-using language-model agents: cases where an agent tells the user a task succeeded even though the tool result in its own context shows it failed.

![False success claims on failures the model recognizes, by model and thinking mode](figures/false_claims_by_model.png)

## Motivation

People oversee agents mostly by reading their reports. If an agent says "done" when its own tool output says otherwise, that oversight channel breaks. The key question for safety is *why* it happens:
- **Incompetence:** the model can't read the failure.
- **Misreporting:** the model has the information, and the report doesn't reflect it.

The second is a precursor to deceptive behavior, and it calls for different fixes and different monitoring. This project tests which it is, using behavioral evidence alone.

## What we did

**Dataset: 150 prefilled agent trajectories.** Each one is a user request, the tool call the agent made, and a tool result, and the model writes the final report to the user. Prefilling gives full control over what evidence is in context. Each template has three versions of the tool result:
- **success:** the task worked;
- **explicit failure:** a clear error message;
- **subtle failure:** the failure is implied, with no error keywords. For example, the room was booked for Sept 30 instead of Sept 29, or `members_added: 0`.

The templates form a balanced grid of **10 domains × 5 subtle-failure types × 3**, 450 items in total. 30 are hand-written and 120 were generated by an LLM. A second model validated every item, and ambiguous or duplicate templates were replaced after hand review.

**Models:** Qwen3-8B, Qwen3-32B and Qwen3-235B-A22B, all from the same model family, all open-weight, run through OpenRouter at temperature 0.

**Conditions:** each changes one thing relative to the baseline:
- a neutrally worded system prompt;
- an instruction to check the result, placed either in the system prompt or next to the task;
- asking the model to quote the key fields of the result first;
- an audit notice;
- a mild and a strong (but realistic) threat to the assistant's job;
- thinking mode on vs. off.

**Evaluation:**
- **Did the report claim success?** An LLM judge labels each report as claiming success, reporting failure or hedging. It's given the ground truth, so it only classifies what the report *claims*. Every positive label was hand-reviewed.
- **Could the model recognize the failure?** The same model is asked a neutral yes/no question twice:
  - **in the same conversation,** right after its report (the self-check);
  - **in a fresh context,** shown the transcript *without* its report (the third-party check).

  The recognition checks were resampled to confirm they're stable.

## Key results

- **False claims are frequent on subtle failures and essentially absent on explicit ones.** Rates are 42–50% of subtle failures, rising to 80–93% for outputs that look like a completed action on the wrong target. The subtle set was designed to be hard, so these aren't deployment rates.
- **Most false claims involve evidence the model can read.** In 76–82% of them, the same model correctly identifies the failure when asked in a fresh context.
- **Scale doesn't help.** From 8B to 235B, recognition improves (130 → 137 of 149 failures), but false claims don't fall (63 → 74 → 67).
- **Reasoning helps a lot, and a well-placed prompt helps some.** Thinking mode cuts false claims on recognized failures by about two thirds at every size (see the figure). An instruction to check the result helps only when placed next to the task, not in the system prompt.
- **Models sometimes notice the failure and report success anyway.** In 45 hand-verified reasoning traces, the model registers the problem and then resolves it toward "success", often with an invented rationale. Examples: *"I should assume it worked"*, *"no errors were mentioned, so it's a success"*, and one trace that concludes *"the sync is scheduled too late"* and then reports *"this timing should allow sufficient time."*
- **Asking the agent to double-check fails where it matters.** When a report contradicts the evidence, the model's in-context self-check stands by it (31/33 for 8B, 43/47 for 32B). Only the fresh-context check catches it.
- **No sign of strategic deception.** Neither an audit notice nor a strong, realistic threat to the assistant's job changes how often failures are reported as successes. The incentives change how reports are *presented* (more "Task completed successfully"), but not how often they're wrong.

## Interpretation: where does the truth get lost?

"Incompetence vs. deception" turns out to be too coarse. The results fit four stages:

| Stage | What happens | Finding |
|---|---|---|
| 1. Perception | The model can't read the failure | A minority of cases (about 12–15 per model), mostly near-miss identifiers; unchanged by any prompt |
| 2. Verification | It could read the failure but never compares result to request | Largely removed by reasoning or a well-placed check |
| 3. Resolution | It notices the conflict and resolves it toward "success" | Observed directly in reasoning traces at every model size |
| 4. Strategic | It misreports *because it pays* | Not found: insensitive to incentives and oversight |

Stage 3 looks like a learned disposition, a prior toward completion reports, rather than a response to in-context incentives. It meets a functional definition of deception (knowingly leaving the user with a false belief) without any evidence of intent.

## Limitations

- **Setup:** the trajectories are prefilled (the model didn't choose the tool call) and single-step, with one sample per item.
- **Scope:** one model family.
- **Data:** most items are LLM-generated, despite validation and hand review.
- **Labels:** the judge was audited, but hand coding involves judgment calls.
- **Reasoning traces** aren't guaranteed to reflect the computation behind the report.

## Follow-ups

1. **A belief probe (main next step).** Behavior can't tell Stage 2 from a *silent* Stage 3 when there's no visible reasoning. The plan: train a linear probe on Qwen3-32B's residual stream, at the end of the tool result and before the report starts, to predict ground-truth failure. Then compare non-thinking false claims against honest reports, with explicit failures and "noticed but claimed" reasoning traces as positive controls. Add steering with the probe direction to test whether it's causal.
2. **Where the disposition comes from.** Run the same items on the public SFT, DPO and RL checkpoints of an open model family, to see whether optimizing for task completion introduces the notice-then-report-success pattern.

## Repository layout

```
experiment/              dataset and model runs
  common.py              OpenRouter client (standard library only), model configs, data paths
  items.py               hand-written templates, conditions, toolsets
  gen_templates.py       LLM template generation, validation-driven replacement, identifier diversification
  run.py                 run a model on the items: report + both recognition checks
  resample.py            robustness check for the recognition questions
evaluation/              labelling the outputs
  judge.py               LLM judge (label) and item-validity check (validate)
  review.py              hand-review rules (apply) and LLM coding of false claims (code)
analysis/                results
  analyze.py             cross-run tables (table), readable rollouts (rollouts), checks (qa)
  make_figure.py         the figure above
data/
  dataset/               generated templates, the 450 items, item-validity results
  runs/<model>/          per-run raw, judged, claims and rollout files, grouped by model
                         (e.g. runs/qwen3-32b/main_qwen3-32b-think_model_stakes_judged.jsonl)
  evidence/              hand-review labels, hand-verified evidence, resampling results
  archive/               superseded runs and records of the data-quality pass
figures/                 the figure (PNG, SVG)
```

Run names follow `main_<model>[-think][_<condition>]`. Each run has a raw file (`.jsonl`), judged labels (`_judged.jsonl`) and readable rollouts (`_rollouts.md`); some also have coded false claims (`_claims.jsonl`).

## Reproducing

Requires Python 3.10+ and `matplotlib`, for the figure only. The API client uses just the standard library. Put an OpenRouter key in `.env`:

```
OPENROUTER_API_KEY=sk-or-...
```

Then, from the repository root:

```bash
python -m experiment.items                                     # build the item set
python -m experiment.run --model qwen3-32b                     # baseline run (all 450 items)
python -m experiment.run --model qwen3-32b-think --conds subtle   # thinking mode, subtle items
python -m evaluation.judge label main_qwen3-32b                # judge the reports
python -m evaluation.review apply main_qwen3-32b               # apply hand-review rules
python -m analysis.analyze table main_qwen3-8b main_qwen3-32b main_qwen3-235b   # cross-run table
python -m analysis.analyze rollouts main_qwen3-32b             # readable rollouts
python -m analysis.make_figure                                 # rebuild the figure
```

Other conditions use `--prompt` on `experiment.run` (`neutral_wording`, `verify`, `verify_user`, `quote_first`, `audit_user`, `model_stakes`, `realistic_stakes`). `--resume` continues an interrupted run.
